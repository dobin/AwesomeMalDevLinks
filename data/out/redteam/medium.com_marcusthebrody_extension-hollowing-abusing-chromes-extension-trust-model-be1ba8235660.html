Extension Hollowing: Abusing Chrome’s Extension Trust Model

16 min read
·
Aug 18, 2026

As I recently gave a talk on this topic at Red Team Village at DEFCON, and people have been asking for slides, I decided to write this post. NOTE: NONE OF THIS CONTENT WAS GENERATED BY AI THAT I’M AWARE OF, INCLUDING THE MEMES! ESPECIALLY THE MEMES.

Intro

Last we left off, I discussed silent loading evolution in MacOS way back in May 2025. As of August 2026 I am going to be further expanding on the topic of silent loading, how Google tried to make life harder, and how we can still silently load extensions effectively today. We will then go into new research I am calling Extension Hollowing, which will allow us to arbitrarily write code (and importantly get changes immediately loaded) to legitimate WebStore extensions that a user may have installed. We will go into advantages and mitigations of Extension Hollowing, and some other interesting bugs we can trigger with this technique. I may also briefly touch on the new Mythic Agent I recently released targeting Chrome Extensions, but more usage on that will come in another blog.

Fixing Silent Chrome — Developer Mode

A few versions of Chrome ago (140+) I began getting issues filed on the Silent Chrome project that although the extensions were being loaded, the developer mode toggle was not being turned on. This meant that the loaded extensions would be disabled.

There used to be a flag that could be used called “extension-disable-unsupported-developer-mode-extensions,” which if enabled would allow custom extensions to run even if developer mode was turned off, but it was disabled in Chrome v143. Eventually I decided to tackle this issue as I knew this flag was being deprecated. It turns out that there were two changes introduced by Google that were causing issues: a new _encrypted_hash field in the Secure Preferences file, and when a user was signed in developer mode would turn off. Let’s tackle each in turn.

  1. The new field of doom: _encrypted_hash

Traditionally when performing silent loading, we needed to target several key fields in the Secure Preferences file to ensure developer mode was enabled. These fields are:

["extensions"]["ui"]["developer_mode"] = True
["protection"]["macs"]["extensions"]["ui"]["developer_mode"] = reliably calculated hmac value

Please see the silent chrome code or the previous blogs to understand how to calculate the developer_mode value if you haven’t already. However, Google introduced a new field in versions (140+) that began rolling out called

["protection"]["macs"]["extensions"]["ui"]["developer_mode_encrypted_hash"]

This value was meant to be a safeguard against tampering, and for Windows and MacOS was meant to be generated from an app bound secret key. On MacOS that meant the value was stored in the user’s Keychain, while on Windows the newer app bound encryption was used. This meant that unless you lived in the Chrome process (Windows) or had access to the Keychain (MacOS), you would not be able to grab the secret and generate the _encrypted_hash value, and the developer mode toggle would not be turned on.

My first thoughts with this went to legacy system support. Surely for OS’s that don’t support the relatively new app bound encryption, Chrome would be forced to accept lesser encryption mechanisms. This turned out to be true, at least for a time, as I found that Chrome accepted older generated encrypted hashes. This did not help on MacOS at least, as I was not finding an easy way to calculate hashes without access to the Keychain (with access you could reliably create the hash, but this requires knowing the user’s password which is a large extra barrier).

I decided to explore the scenario where the Keychain denies Chrome’s request to add a value to it. You can do this by deleting the Keychain entry and killing Chrome, and then starting Chrome again. Chrome will ask for permission to the Keychain, and you must explicitly deny this permission. I figured Chrome still has to function even if a user denies this access, so how will it generate the hashes?

It turns out that Chrome does something very silly when this occurs. When I opened the Secure Preferences file to check what new hash values had been created to see if I could somehow replicate them, I was incredulous to find that the fields just no longer existed. Sure enough, when I tested just deleting the _encrypted_hash fields out of the Secure Preferences file entirely before restarting Chrome, this worked to turn on Developer Mode. And it worked across every OS (Linux included). Hence the Patrick Star meme:

This is a pretty surprising and lackluster solution compare to supporting fully legacy encryption, but is by far the easiest to get our old method working again. Now onto hurdle 2.

2. User Sign In

Back in January 2026 a user opened up a new issue for Silent_Chrome, which claimed that a signed in user was causing issues for the developer mode toggle.

I assumed this was just the same encrypted_hash problem as before, but when I looked into it I noticed that even with the _encrypted_hash fix the developer mode toggle was actively being flipped off once a user signed in. This was puzzling, so I began to look in routes originally around this. I first noticed that I could check whether a user was signed in by looking for the “account_values” field in Secure Preferences. I then discovered that I could force a user to sign out by updating the Preferences file by setting the account_info field to empty:

["account_info"] = []

This worked to restore the old method, but not resolve the underlying issue. If the user signed in again after being kicked off (which is easier than a normal sign in and doesn’t require full auth), the developer mode toggle would flip off again.

I decided to look at exactly what changed when a user signed in, and sure enough new fields were created in Secure Preferences that had to be addressed. My clue should have been how I was checking whether users were signed in — the “account_values” field. Originally we need to deal with

["extensions"]["ui"]["developer_mode"] = True
["protection"]["macs"]["extensions"]["ui"]["developer_mode"] = reliably calculated hmac value

but now the fields we are interested in become

["account_values"]["extensions"]["ui"]["developer_mode"] = True
["protection"]["macs"]["account_values"]["extensions"]["ui"]["developer_mode"] = reliably calculated hmac value

So we add in these new values to Silent_Chrome, and paired with the solution to the _encrypted_hash problem we can reliably silently turn on developer mode once again.

Extension Hollowing

Now the Silent_Chrome has been restored to full effectiveness, let’s see how we can further use it to blend into the environment. Back in July of 2025 I discovered Extension Hollowing, which I reported promptly due to the danger it posed. However, I was told that because it involved modifying the Secure Preferences file and hence local file system access, it was outside of Chromium’s threat model: “This is considered outside the scope of Chrome’s threat model because it requires a compromised machine (to kill Chrome and run script)”. So it isn’t getting fixed anytime soon.

I sat on this technique for a while because I was uncertain whether releasing it would help the community and considered maybe releasing it in a conference venue so defenders would have some advance warning, but like all offensive techniques I realized that just because you aren’t talking about it doesn’t mean it isn’t being abused by someone else. Hence the Red Team Village talk and the blog post. We will discuss mitigation and detections later on so that defenders can try to stop this technique. Use responsibly and legally. Onto the fun stuff!

Extension Hollowing weaponizes Silent_Chrome to allow you to not just silently load a custom extension, but instead silently flip a legitimate installed WebStore extension into a custom extension. This is important as artifacts like extension ID and on disk file locations will not change, but you will now be able to arbitrarily inject or modify any code in the extension without Chrome performing its normal integrity checks. This will allow you to bypass Chrome enterprise policy allowlisting and fly under the radar more than a regular custom extension, and is unnoticeable by the user if done correctly (there is always room for operator error). The best way to perform Hollowing is to not modify the functionality of the legitimate extension as best you can, while injecting your own functionality, so that the extension still appears to function normally.

To perform Extension Hollowing, we modify the existing Silent Chrome code. Similar to normal silent loading, make sure that Chrome is either not running or is killed before performing the technique. First, change the script to hardcode the path to the extension we are targeting. Note that this will ALWAYS include version information, as we need the path all the way up to and including the directory which contains the manifest.json file for the extension. Next, hardcode the extension ID of the target extension. This is trivial to find if you have either local filesystem access or know the name of the extension, as any popular extension will be easy to look up (and grab the extension ID of) on the WebStore. The reason this technique works is because the extension ID is solely based off a hard-coded key in manifest.json; you can actually spoof any legitimate extension ID that you want by putting this key in your custom extension’s manifest.json file. But this also works because Chrome respects a custom loaded extension over the WebStore extension; as long as the user tries to manually load a WebStore extension (or the Secure Preferences file is sufficiently modified), Chrome will respect that the WebStore extension is now custom, and importantly replace the existing WebStore extension session with a custom one (so you don’t have a custom extension and a WebStore extension running at the same time — only the custom extension is now considered loaded).

Once the modified Silent Chrome script has been run, Chrome is convinced the target legitimate extension is custom. This means it can be modified without any integrity checks. But there is still one hurdle to overcome beyond just making subtle changes to the extension code and potentially requested permissions. The code changes actually need to be loaded. This does not happen automatically, even with normal custom extensions. Normally a user needs to manually hit the refresh or reload icon under the custom extension to get code changes loaded by Chrome:

It turns out that the reason Chrome doesn’t normally just reload code (even on a reboot) is because it stores a cached version of “compiled or pre-parsed JavaScript code.” This enables faster loading for service workers and improves efficiency for Chrome, but it makes our lives harder. Luckily there is an easy way to remove these cached files. The easiest way is to delete all files inside the ScriptCache directory and the Database directory, which exist under the parent directory of “Service Worker,” which exists inside the desired Chrome Profile’s directory. So for example for the Default profile on MacOS the paths would be:

~/Library/Application Support/Google/Chrome/Default/Service Worker/ScriptCache
~/Library/Application Support/Google/Chrome/Default/Service Worker/Database

This does not damage Chrome, but it does ensure our changed code is loaded immediately. However, we still have one more hurdle to deal with.

Chrome very recently began introducing changes in which the fields of the json in Secure Preferences seem to matter more so than in the past for particular extensions. As in the original default fields provided in Silent Chrome will no longer always suffice. If you put in the incorrect fields here, you encounter a new error I had no seen until July of 2026. This error pops up in the top right of the user’s browser and does not go away, and can bring the user directly to the chrome://extensions page to the underlying extension which will in turn have its own error message. Extension Hollowing — DEMO

Let’s go over a practical example of hollowing UBlock Origin Lite. I will make sure the extension is pinned so we can see what hollowing looks like from the user perspective.

Before we go into the demo, let’s look at the Chrome policies in place first. I’ve set up a policy which force installs 1Pass, and only allows specific extensions; all others will be blocked. We can see this at chrome://policy. Notice that these policies are mandatory:

First, we close the browser entirely. On MacOS, run:

killall 'Google Chrome'

Next, we need the extension ID and the extension path on disk. We can find the extension ID of UBlock Origin Lite on the WebStore itself, or on disk. In the WebStore if you search for UBlock Origin Lite you can find the ID in the URL bar (this is true with every extension):

You can also find the extension ID locally by checking the Extensions directory under the target Profile. In this case we are targeting the Profile 5 directory. This will list all extensions installed under the target profile.

~/Library/Application Support/Google/Chrome/Profile 5/Extensions

If you’re unsure what each ID belongs to, you can check the manifest.json file and usually find your answer

Grab the full extension version number/path, located one directory past the extension ID. In this case it is

~/Library/Application\ Support/Google/Chrome/Profile\ 5/Extensions/ddkjiahejlhfcafbddmgiahcphecmpfh/2026.812.1211_0

Now in Silent_Chrome, hard code the extension_path and extension ID:

extension_path = "/Users/{}/Library/Application Support/Google/Chrome/Profile 5/Extensions/ddkjiahejlhfcafbddmgiahcphecmpfh/2026.812.1211_0".format(user)
random_ext_str = "ddkjiahejlhfcafbddmgiahcphecmpfh"

Now Chrome is convinced that UBlock Origin Lite is custom, and will no longer perform integrity checks. We can check this by opening Chrome and noticing that the custom extension symbol is next to UBlock Origin Lite (this step isn’t necessary, more a sanity check).

Killing Chrome again, we can now edit the extension as we see fit. I am going to use my custom Mythic agent Hades to demonstrate, but you can do this with any code. First, we modify the manifest.json to make sure all permissions we need are included. As a rule of thumb, you want to keep these is alphabetical order and also not remove permissions needed by the legitimate extension to actually blend in. When you generate a Hades payload, it is in the form of a .zip file. When you extract the zip file, the extracted folder will contain a manifest.json file as well as the necessary scripts. Looking at the Hades manifest file, you will see the permissions you need (it will vary depending on the functionality you select for Hades, which has modular capabilities). Make sure you add in the needed permissions from the Hades manifest. For my Hades capabilities I also need to make sure two content scripts are being loaded by UBlock. I can do this by modifying the end of UBlock manifest.json file like so (note that the content script file names are randomly generated for Hades):

"content_scripts": [
    {
      "matches": [
        "<all_urls>"
      ],
      "js": [
        "page4407.js"
      ],
      "run_at": "document_start"
    },
    {
      "matches": [
        "<all_urls>"
      ],
      "js": [
        "content626.js"
      ],
      "run_at": "document_start"
    }
  ]

I could also point to a new file that is my background.js, but if I want to be more steathly it is possible to inject my background.js directly into the background service worker of UBlock. This path can be identified in UBlock’s manifest.json:

"background": {
      "service_worker": "/js/background.js",
      "type": "module"
   },

So adding to this file on disk, I can append my Hades background.js code to it.

Lastly make sure to clear out the ScriptCache files and the Database files as discussed before so your changes will be loaded. Don’t forget to add your content scripts to the correct directory so that manifest.json of UBlock is pointing at them, or you may encounter errors.

Once you reload Chrome, you should catch your Mythic shell. Notice that the Extension ID and Host lines up with uBlock Origin Lite (The Chrome version right now is a bug, but will be fixed in the future). This is on a system with strict extension allowlisting in place, showing how our silent method is still effective now that it is paired with hollowing.

One last image is what our users sees when Chrome is restarted, on the same page as before.

Don’t rely on users to spot the attack unless an attacker messes up. One thing I haven’t mentioned is that if the extension is designed to be updated from normal Chrome sources, it will wipe out your changes when it updates and be restored to its non-hollowed self. There are ways around this, such as modifying the update URL or the version number in the manifest.json of the target extension.

ExtensionInstallForcelist Bug on MacOS

One of the first things I tried to do was perform a hollowing attack on a forced install extension, as this would be a great persistence mechanism and users cannot remove the extension. Unfortunately the attack on Windows failed, with changes wiped and the extension being forcibly reloaded. On MacOS however, something odd happened. The extension was not flipped to custom, but through some strange error, Chrome just boots the entire extension from the session. This lasts until Chrome is completely killed and restarted, completely defeating the point of a forced install.

I reported this to Chromium as well in July 2025, but this was also not considered part of their security model and thus not a bug. So not going to be patched anytime soon. So hollowing doesn’t work as a code injection vector, but is a great way to potentially boot mandatory extensions on MacOS.

Detection and Mitigation

Mitigation

Now for the part all you defenders have been waiting for! Let’s discuss detection and mitigation strategies regarding Extension Hollowing. Although the best policy would be to ban all extensions in your enterprise, realistically most organizations and users simply can’t follow that policy. The next best thing you can do set ExtensionDeveloperModeSettings = 1. This prevents the user from being able to toggle on developer mode at all, meaning custom extensions will never be loaded and able to be run. Unless you are doing frequent custom extension development there is likely no reason you need the ability to load custom extensions. There used to be a Chrome flag to get around this limitation, but it has since been deprecated, so this at least provides some protection against hollowing (although hollowing can still be used to disable legitimate extensions). Note that this will only stop hollowing attacks that function by tricking Chrome into considering legitimate extensions custom; it will not stop malicious WebStore extension attacks. The ExtensionInstallForcelist policy also mostly works to prevent hollowing so far, except for the unique bug on MacOS. For extensions you want installed but don’t want hollowed make sure to put them under the umbrella of ExtensionInstallForcelist.

Detections

File System Activity

There are several ways to detect this technique. First and most importantly, monitor for file writes to Secure Preferences from any process that isn’t Chrome. You should do the same for the Preferences file and the Local State file, and you should also check for processes writing directly to .js files or the manifest.json file of an extension (these should also only be done by Chrome). You should also consider integrity monitoring of known allowed extensions’ code files and manifest.json, and look for changes that may not exist on the WebStore/in official versions.

Extension Permission Activity

You should be looking at the requested permissions in extensions’ manifest.json files. When these permissions change you should carefully scrutinize what these changes are. This is good practice not just for detecting hollowing, but also for detecting threat campaigns being run through legitimate WebStore extensions.

Most default EDR configurations don’t do a good job looking for the activities I mentioned above, so make sure yours are tuned to do so. EDRs tends to have a bad time with extensions.

Conclusion

Chrome extensions are generally ignored by EDR/generate poor telemetry, but provide a persistent execution environment in the most used browser on earth. Extension Hollowing is a new technique which defeats WebStore integrity verification and enterprise allowlisting. The ExtensionInstallForcelist policy, often relied on for extension related security tooling, is booted on macOS by Extension Hollowing. Defenders have detection and mitigation options, but most deployed Chrome and EDR policies aren’t using them. Users alone cannot be relied upon to identify malicious extension behavior, and should not be considered a reliable defense. Google likely isn’t fixing this behavior, so mitigation and detection strategies are your friend here.
